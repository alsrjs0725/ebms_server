# 관리자 페이지

`EBMS_ADMIN_USER_IDS`에 계정 ID(UUID)를 넣은 사용자나 관리자 페이지에서 admin으로 지정된 사용자는 `/admin`을 쓸 수 있습니다(`/account`에 링크). `EBMS_ADMIN_USER_IDS`는 승격만 하고 강등은 하지 않으므로, 관리자를 내리려면 관리자 페이지에서 role을 바꿉니다. 관리자 API는 웹 세션 쿠키로만 쓸 수 있고, 로그인하지 않았으면 `401`, 관리자가 아니면 `403`입니다.

- 전역 기본값 일괄 수정: 최대 티켓, 리필 시간, 같은 곡 재차감 없음 시간, 사전 다운로드 월 한도, 초과 후 속도. 처음 시작할 때 기본값을 넣고, 이후 바꾼 값은 재시작해도 유지됩니다.
- 사용자 검색(닉네임·계정 ID), 사용자별 한도 덮어쓰기(비우면 전역 기본값), 티켓 즉시 충전, 정지·해제.
  - 사용자 목록·상세를 보거나 바꾸면 관리자 접속기록을 남깁니다: `var/log/audit.log`(1년 이상 보관)와 서버 로그(로거 `ebms_server.audit`). 한 줄에 관리자 id, 접속 IP, 행위(`user.search`·`user.view`·`user.update`·`user.refill`·`download.search`), 대상 사용자 id(검색이면 결과 전체), 검색어·바꾼 값이 들어갑니다. 안전성 확보조치 기준에 따라 월 1회 이상 로그 화면에서 이 로거로 걸러 점검합니다.
- 메인화면(`/admin/home`): 메인화면(`/`) 위쪽과 로그인 화면(`/login`) 아래쪽에 보일 소개 글, 클라이언트 다운로드 링크, 문의 연락처 등을 적습니다. 저장하면 바로 반영되고(`site_text` 테이블, 이력 없음), 저장한 적이 없으면 기본 글(소개 + 클라이언트 GitHub 릴리스 링크 + 문의 칸)을 보여줍니다. 비워서 저장하면 아무것도 보여주지 않고, 채우지 않은 칸(`[[...]]`)이 있는 줄은 메인화면에서 뺍니다. 문법은 처리방침과 같은 마크다운 일부입니다.
- 공지(`/admin/notices`): 클라이언트가 켜질 때 띄울 공지를 쓰고 고치고 지웁니다. 게시 여부와 시작·종료 시각을 정할 수 있고, 클라이언트는 사용자가 확인한 공지를 다시 띄우지 않습니다(고치면 다시 띄움).
- 처리방침·약관(`/admin/policies`): 개인정보 처리방침(`/privacy`)과 이용약관(`/terms`)을 고칩니다. 저장한 적이 없으면 `src/ebms_server/policy_templates/`의 기본 템플릿을 보여주며, 템플릿의 `[[...]]` 칸(운영자 이름, 연락처, 보유기간 등)을 채워 저장하세요. 저장할 때마다 시행일과 함께 새 판(`policy` 테이블)으로 쌓여 공개 페이지에 변경 이력으로 보입니다. 시행일을 미래로 두면 그날까지 지금 판을 보여주면서 "변경 예정"을 알립니다. 두 페이지는 로그인(가입) 화면, 메인, `/account`, 모든 페이지 아래에 링크됩니다. 본문은 마크다운 일부(제목, 목록, 표, 굵게, http(s)·mailto 링크)만 지원합니다.
- 다운로드 기록(`/admin/downloads`, 사용자 카드의 **다운로드 기록** 버튼): 곡 플레이 다운로드(곡 zip) 요청을 최신순으로 봅니다(`download_log` 테이블, 한 쪽에 50개). 닉네임·계정 ID, 곡 번호, 결과(받음(티켓 차감)·받음(재차감 면제)·티켓 없음·동시 다운로드 초과·없는 곡·지운 곡)로 거르고, 이어받기 요청은 따로 표시합니다. 프록시 뒤에서는 `/api/proxy/authz`가, 직접 받을 때는 `/api/play/song`이 기록하며 "받음"은 전송을 허락했다는 뜻입니다(끝까지 받았는지는 모름). 304·416과 사전 다운로드는 남기지 않습니다. 90일(`EBMS_RETENTION_DOWNLOAD_LOG_DAYS`)이 지나면 지우고, 조회하면 접속기록(`download.search`, 결과에 나온 사용자 id)을 남깁니다.
- 곡 관리(`/admin/songs`): 곡 번호·폴더명·차트 파일명으로 곡을 찾고(최근 등록 순, 한 쪽에 50곡), 곡을 누르면 곡 zip의 파일 구조(폴더별, 차트·사전/플레이 표시, 종류별로 보이기/숨기기. 두 종류에 속한 파일은 둘 다 끄면 숨김)를 보고 파일 하나나 zip 전체를 받습니다(티켓·사용량을 쓰지 않음). **사용 중지**(삭제)는 사유를 적고 곡 번호를 다시 입력해야 합니다. 곡 zip과 차트(곡 zip에 없는 차트는 차트 청크에서 꺼냄)를 `var/unused/{곡 번호}/`(`song.zip`, `charts/{sha256}{확장자}`)로 옮기고 DB의 곡 데이터를 지웁니다. 사용 중지한 곡은 **사용 중지** 탭(`deleted_song` 테이블)에 폴더명·크기·차트 수·사유·지운 사람·시각과 함께 남고, 번호는 결번으로 두어 다른 곡에 쓰지 않습니다(AUTO_INCREMENT가 되돌아가도 결번 뒤부터 씀). **복원**하면 같은 번호로 되돌리고 옮겨 둔 폴더를 지웁니다. 복원할 차트가 다른 곡에 붙어 있으면 `409`로 복원하지 않습니다. 사용 중지·복원하면 그 곡의 매니페스트·사전 청크를 다시 만들어 클라이언트는 다음 동기화 때 목록에서 빼거나 다시 받습니다. 사용 중지한 곡을 요청하면 `410` `song deleted: <사유>`입니다. 차트 청크에서는 뺄 수 없어 차트는 곡 연결만 끊어 남깁니다. 사용 중지한 곡과 차트(sha256+크기)가 하나라도 겹치는 곡은 다시 임포트하지 않고 건너뛰며(경고 로그, 작업 결과에 `skipped: "unused"`와 그 곡 번호), 검토 대기에서도 빠집니다. 다시 쓰려면 복원합니다. 임포트 배치가 쓰기 잠금을 10초 넘게 잡고 있으면 `409`이므로 잠시 뒤 다시 시도합니다.
- 난이도표(`/admin/tables`): 난이도표 주소(HTML 또는 헤더 JSON)를 등록하면 beatoraja와 같은 방식(HTML의 `<meta name="bmstable">` → 헤더 JSON의 `data_url` → 차트 목록)으로 읽어 차트의 md5·sha256·레벨을 저장합니다(`difficulty_table`, `difficulty_table_chart`). 사전 청크마다 그 청크에 곡이 있는 표가 태그로 붙고([`GET /api/pre/tables`](api.md)), 클라이언트는 고른 표의 청크만 받을 수 있습니다. 표마다 서버에 있는 차트·곡 수와 마지막으로 읽은 시각이 보입니다. **다시 읽기**로 바로 갱신하고, 서버는 `EBMS_TABLE_REFRESH_HOURS`(기본 24, 0이면 끔)마다 모든 표를 다시 읽습니다. 읽지 못하면 이전 목록을 그대로 두고 오류만 보여줍니다. 이전 버전에서 넣은 차트의 md5는 서버 시작 뒤 백그라운드에서 차트 청크를 읽어 채우며, 다 채우기 전에는 sha256을 주는 표만 맞습니다.
- 곡 임포트(곡 관리의 **곡 임포트** 탭, `/admin/import`로 바로 열림): zip·rar·7z를 올리거나 서버의 `var/tmp/`를 가져오면 곡을 바로 등록하지 않고 **검토 대기**(`var/staged/`)에 둡니다. 검토하고 **commit**해야 DB에 들어갑니다. 서버를 시작할 때는 `var/tmp/`를 가져오지 않습니다. 차트 파일이 있는 폴더가 곡 하나이고, zip 최상위에 차트가 있으면 zip 이름을 곡 폴더명으로 씁니다. UTF-8 플래그가 없는 zip의 파일 이름은 UTF-8, cp932, cp949 순서로 읽습니다. 차트(BMS) 헤더는 차트마다 `#`로 시작하는 줄 전체를 UTF-8·cp932·cp949로 풀어 보고 오판 흔적(반각 가타카나, KS X 1001 밖 확장 한글)이 가장 적은 인코딩으로 읽습니다. 어느 것으로도 풀리지 않으면 대체 문자로 넘기지 않고 그 곡을 **등록 불가**로 검토 대기에 남깁니다(commit해도 넣지 않음, '등록 불가·commit 실패·충돌'로 거르기). 검토 대기의 곡은 **내려받기**로 곡 파일(zip)을 받아 확인할 수 있으니, 등록 불가 곡은 받아서 고친 뒤 다시 올리고, 대상을 **제외**로 두면 commit 때 묶음에서 빠집니다. rar는 분할 압축(`이름.part1.rar`·`이름.part2.rar`…, 또는 `이름.rar`·`이름.r00`…)도 받으며 서버의 `unrar`로 풉니다(도커 이미지에 들어 있음). 웹에서는 볼륨을 모두 함께 선택해 올리고, rar 최상위에 차트가 있으면 rar 이름(`.partN.rar` 등을 뗀 이름)을 곡 폴더명으로 씁니다. 암호가 걸린 rar는 풀지 않습니다. 7z는 서버의 7-Zip으로 풀고(도커 이미지에 들어 있음), 파일 이름이 유니코드로 저장되므로 인코딩을 고르지 않습니다. 7z 최상위에 차트가 있으면 7z 이름을 곡 폴더명으로 씁니다. 7z 분할 압축(`.7z.001`…)과 암호가 걸린 7z는 받지 않습니다. 곡 폴더 안의 심볼릭 링크(파일·폴더)와 일반 파일이 아닌 항목은 따라가지 않고 건너뛰며 경고 로그를 남깁니다.
  - 브라우저가 zip을 조각(처음 32MB, 프록시가 `413`을 주거나 연결을 끊으면 절반씩 줄여 최소 256KB)으로 나눠 `var/import/`에 이어 붙이므로, 앞단 프록시의 요청 크기 제한과 상관없이 수십 GB도 올릴 수 있습니다. 끊기면 받은 곳부터 다시 보냅니다(약 10분까지). 받는 중인 업로드는 `var/import/{id}.json`에 이름·크기를 적어 두므로 그동안 서버가 다시 시작돼도 이어 받고, 24시간 동안 조각이 오지 않은 업로드는 지웁니다.
  - 다 받으면 서버가 백그라운드에서 곡을 하나씩 검토 대기 묶음에 풀고 zip을 지웁니다. 디스크는 zip 크기 + 2GB가 필요하고(모자라면 시작할 때 `507`), 푼 곡은 commit하거나 폐기할 때까지 `var/staged/`에 남습니다. 곡은 낱개 파일로 풀지 않고 곡마다 압축하지 않은 zip 하나(`{묶음}/{곡}/song.zip`)로 두어, 작은 파일(키음 등)이 디스크 할당 단위만큼씩 차지해 크기가 부풀지 않게 합니다. commit할 때 곡 하나씩 작업 폴더에 풀어 넣고 바로 지웁니다. 임포트 캐시(`EBMS_CACHE_DIR`, SSD 등)를 켜 두면 한도 안의 업로드와 묶음은 캐시에 두고, 검토 대기 위에 캐시 사용량이, 캐시에 둔 묶음에는 "캐시" 표시가 나옵니다(docs/deployment.md#ssd를-작업-공간으로-쓰기). 진행 상황은 페이지의 **작업**에 보이며, 다 올린 뒤에는 페이지를 닫아도 됩니다. 작업 목록은 메모리에만 있어 재시작하면 비워지고, 재시작 시 `var/import/`의 받던 업로드 말고 남은 파일은 지웁니다. 다 받은 파일은 묶음의 `_source/`로 옮겨 다 풀 때까지 두므로, 풀다가 꺼져도 다시 시작할 때 마지막 저장(2초마다) 뒤의 곡부터 이어서 풉니다(작업에 "서버 재시작 후 이어서" 표시).
  - rar·7z는 곡 하나씩이 아니라 통째로 풀므로 rar·7z 크기 + 2GB의 여유 디스크가 더 필요합니다(모자라면 끝낼 때 `507`). 볼륨이 빠졌거나 깨졌으면 작업이 실패하고 묶음을 만들지 않습니다.
  - **var/tmp 가져오기**는 곡 폴더를 묶음으로 옮기고(`var/tmp/`에서 사라짐), zip·rar·7z는 풀고 다 풀었으면 지웁니다. rar 분할 압축은 볼륨을 모두 `var/tmp/` 바로 아래에 둡니다.
  - 검토 대기: 묶음(zip·7z나 rar 하나, 또는 var/tmp 가져오기 한 번)마다 곡의 판정을 보여줍니다. 새 곡, 기존 곡에 추가(차트가 겹치는 곡), 여러 곡과 겹침, 사용 중지 곡과 겹침, 비슷한 곡 있음. 곡마다 넣을 곳을 **자동**(판정대로), **새 곡**, **기존 곡에 추가**(검색 목록에서 곡을 고름. 검색어가 없으면 판정에 나온 곡을 먼저 보여줌), **제외** 중에서 고르고, 채보를 펼쳐 채보마다 따로 고를 수도 있습니다(기본은 곡 설정 따름). 판정·폴더명으로 거르고, 넣은 순서나 파일 수 순으로 정렬해 볼 수 있습니다.
    - 비슷한 곡 있음: 파일이 50개 미만인 곡(보통 기존 곡의 추가 채보)은 겹치는 채보가 없어도 `#TITLE`(끝의 `[ANOTHER]`·`(7KEYS)`·`-HYPER-` 같은 난이도 표기, 대소문자·전각·공백 차이는 무시), `#ARTIST`(`/` 뒤의 채보 제작자 표기는 무시), `#BPM`, `#GENRE` 중 2개 이상 같은 기존 곡을 후보로 보여줍니다(많이 겹치는 순, 같은 항목 표시). 곡에 없는 키음(`#WAV`)이 있으면 기존 곡에 그 키음이 몇 % 있는지(음원 충족률)도 보여주고, 100%인 곡은 항목이 하나만 같아도 후보이며 먼저 나옵니다. 가장 앞선 곡이 하나이고 그 곡에 없는 키음이 없으면(곡에 없는 키음이 없는 곡은 따지지 않음) **자동**은 그 곡에 추가하고, 아니면 새 곡입니다. 파일이 50개 이상인 곡은 겹치는 채보로만 판정합니다. 이전 버전에서 넣은 차트의 헤더 값은 서버 시작 뒤 백그라운드에서 차트 청크를 읽어 채우며, 그 전에는 후보로 나오지 않습니다.
    - 채보를 펼치면 채보마다 이름·작곡가·BPM·장르와 상태가 보이고, **채보 외 파일**을 열면 키음·이미지 등 나머지 파일 목록을 따로 봅니다.
    - 새 곡으로 지정해도 이미 다른 곡에 있는 채보는 원래 곡에 둡니다. 채보가 모두 이미 등록돼 있으면 새 곡을 만들지 않고 실패로 남습니다.
    - 채보를 여러 곳으로 나누면 곳마다 그 채보, 그 채보가 가리키는(`#WAVxx`·`#BMPxx`·`#BANNER` 등) 파일, 어느 채보도 가리키지 않는 파일을 묶어 넣습니다.
    - 판정은 묶음을 만들 때와 commit 뒤에 다시 하고, **다시 판정**으로 지금 DB 기준으로 다시 할 수 있습니다. 묶음은 디스크(`var/staged/{묶음}/stage.json`)에 있어 재시작해도 남고, 풀거나 commit하던 중에 꺼졌으면 다시 시작할 때 그 자리부터 이어서 합니다(commit은 커밋한 배치까지 등록돼 있고 나머지 곡부터, var/tmp에서 옮기던 곡은 var/tmp로 되돌렸다가 다시 옮김). 5번 이어서 해도 끝나기 전에 꺼지면 멈추고 검토할 수 있게 둡니다.
  - commit은 아래 배치로 등록합니다. 잘 들어간 곡과 제외한 곡은 묶음에서 빠지고, 실패하거나 충돌(같은 경로에 내용이 다른 파일)이 난 곡은 결과와 함께 남아 다시 고치거나 폐기합니다. 곡이 다 빠지면 묶음도 지웁니다. **폐기**는 묶음을 등록하지 않고 지웁니다.
  - commit은 곡 여러 개를 한 트랜잭션(배치)으로 넣고, 차트·매니페스트·사전 청크는 배치를 커밋할 때 한 번씩만 갱신합니다. 새 차트 64MB, 곡 데이터 1GB, 500곡 중 먼저 차는 쪽에서 커밋합니다(`IMPORT_BATCH_*`). 도중에 꺼지면 그 배치는 통째로 롤백되고 다시 임포트하면 들어갑니다. 곡 하나가 실패하면 그 곡만 되돌립니다.
